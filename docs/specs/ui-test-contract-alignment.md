## Problem Statement

UI-Test 的主入口已要求新执行与结果契约，但报告、A2A 交接、checkpoint 产物和模块就绪判定仍使用不一致的字段或语义。使用者可能遇到合法 V5 结果无法报告、交接丢失范围和来源、checkpoint 版本被误当主 Packet 版本、合法多阶段流程被阻止，以及证据收集动作无法消费。

POC 阶段还存在与 UI 效果无直接关系的固定 runner 目录、active 发布登记和摘要匹配启动门槛。用户需要可实际运行、可验证、可继续维护的 UI 自动化，而不是仅统一版本字符串。当前发现来自源码静态审计，不代表已完成真实业务复现。

## Solution

以一个统一主 Packet 承载任务与交接信息；由包含完整任务身份的 checkpoint 执行快照生成新 Packet；主入口与子 Skill 共用模块就绪契约。允许“两项独立 UI 特征”或“一项 UI 特征＋本轮 UI 自然请求产生的 HTTP 业务证据”。

默认一次提交，已声明且获授权的多阶段用例按顺序每阶段一次。取消固定目录与发布身份准入，保留目标页面、登录、业务断言、防重复提交、凭据保护以及 V5 结果与证据链。所有网络取证只能监听 UI 自然请求，不额外调用、重放接口或主动 API 轮询。

在本地 UI-TEST 仓库维护相关源码，以实际入口和可见受控网页验收，验证后备份并同步安装副本。旧产物只保留查看，不自动转换后续跑。

## User Stories

1. 作为 Skill 使用者，我希望合法 RunResultV5 能生成报告，以便查看本轮真实执行结果。
2. 作为报告阅读者，我希望失败或未知状态如实显示，以免报告生成成功被当作业务成功。
3. 作为报告阅读者，我希望查看阶段结果、提交次数和证据，以便定位失败环节。
4. 作为报告维护者，我希望旧 v2 和未知版本输入明确报错，以免静默丢失新字段。
5. 作为历史证据使用者，我希望已有报告和失败证据保持原样，以便回溯。
6. 作为交接方，我希望主 Packet 包含目标、约束、历史和修复点，以便接手方获得完整任务信息。
7. 作为接手方，我希望范围、用例、分支、运行和来源链不丢失，以免处理错误任务。
8. 作为接手方，我希望区分主流程动作和交接建议，以免将提示修订误当执行授权。
9. 作为维护者，我希望缺失历史明确标记为未知，以免空列表被误当没有失败。
10. 作为 checkpoint 使用者，我希望可复用定义不包含冒充本轮成功的历史状态，以便安全复用流程。
11. 作为运行者，我希望每次 checkpoint 执行快照带完整身份，以便独立生成正确主 Packet。
12. 作为运行者，我希望不同运行的快照和派生 Packet 身份可区分，以免串用证据。
13. 作为 Skill 使用者，我希望两个独立 UI 特征可以证明模块就绪，以便不依赖网络证据。
14. 作为 Skill 使用者，我希望一个 UI 特征与匹配的 HTTP 业务证据可以证明就绪，以便适应实际页面。
15. 作为运行者，我希望过期、跨会话、无关或业务失败的证据不能证明就绪，以免误操作。
16. 作为运行者，我希望证据不足时如实停止或采用两个有效 UI 特征，以免通过额外接口调用补证。
17. 作为用例维护者，我希望默认仅允许一次提交，以免重复点击造成重复业务写入。
18. 作为用例维护者，我希望预先声明的连续流程可以每阶段提交一次，以便覆盖真实多步骤业务。
19. 作为运行者，我希望前阶段失败或未知时停止依赖它的阶段，以免盲目重试。
20. 作为运行者，我希望已授权完整流程自动进行阶段检查，以免逐阶段重复人工确认。
21. 作为运行者，我希望一个完整用例保持同一浏览器上下文，以便登录和业务状态连续。
22. 作为维护者，我希望动作使用 collect-evidence、状态保留 evidence，以便生产者和消费者一致。
23. 作为 POC 使用者，我希望指定用例能在非旧固定目录且无发布登记时启动，以便验证 UI 效果。
24. 作为运行者，我希望实际脚本来源和执行授权仍可追溯，以免取消发布门槛后丢失事实依据。
25. 作为使用者，我希望所有子 Skill、失败回退和恢复均只监听 UI 请求，以免工具走接口旁路。
26. 作为凭据所有者，我希望请求和证据只保留必要脱敏内容，以免凭据进入产物。
27. 作为维护者，我希望旧运行产物不能在新流程自动续跑，以免历史身份被伪装为本轮事实。
28. 作为维护者，我希望从源用例及真实当前任务生成新产物，以便执行使用有效契约。
29. 作为维护者，我希望相关源码在同一仓库验证，以便后续 Agent 可独立理解和维护。
30. 作为安装使用者，我希望同步前备份并保留已有改动，以便核对和回滚。
31. 作为验收者，我希望节点结果、业务提交、产物提交和外部人工验收分别表达，以免扩大通过结论。
32. 作为验收者，我希望以实际入口和可见网页证明行为，以免仅通过模拟函数或 Schema 校验就宣称 UI 可用。

## Implementation Decisions

### 契约归属与演进

- 主 Packet 是唯一任务交接权威；交接信息放入主 Packet，不另设需要拼接才能恢复完整任务的上下文侧文件。遵从已确认的统一 Packet 与完整执行快照决策。
- 规格固定新运行契约名称：主 Packet 3.0；checkpoint 执行快照 ui-test.checkpoint-execution.v1；ModuleReadyContext 2.0；ExecutionContext 使用 ui-test.execution-context.v4；R2ApprovalRecord 使用 ui-test.r2-approval-record.v3。RunResult 保持 ui-test.run-result.v5，最终提交仍使用 transaction-v1。checkpoint 定义的版本独立，不复制给 Packet。
- 项目配置升级至 2.3、运行契约版本 4，以区分已取消发布准入的新语义；相应运行摘要及消费者同步。已有与本次无关的配置含义保持不变，不顺带重做项目治理。
- 新运行生产者和消费者只接收各自的新契约。旧 Schema/历史产物可留作查看，但不得通过自动转换、默认填值或旧名称别名取得新执行资格。源码在集成完成前不替换安装副本。
- 采用主 Skill 的权威 Schema 和语义校验，子 Skill 复用；避免各自维护一份不同的身份、版本或就绪规则。不新建通用工作流引擎或策略框架。

### 主 Packet 与 A2A

- 保留结构化 scope、case、branch、run、steps、lineage、evidence_policy、retry_policy 和主流程 next_action。scope 包含项目组、产品、系统、模块路径、功能、checkpoint、环境和风险；顶层风险与范围风险不得矛盾。
- 新增 objective、artifact_refs 及主 Packet 内的 handoff 对象。handoff 承载交接建议 action、constraints、history_status、failure_history、retry_history、required_fix_points；不以 handoff 的建议自动授权浏览器或外部模型执行。
- 主流程 next_action 继续使用主路由词汇，其中证据收集只有 collect-evidence；state=evidence 仍合法。revise_prompt、rerun_midscene、fallback_playwright、escalate_human、review 属于 handoff.action，不能填进主流程 next_action。
- history_status 为 complete 或 unknown；complete 且历史数组为空才表示已确认没有记录。unknown 不伪装为空白成功历史，可生成明确标记缺失的交接供查看，但阻止依赖既往失败/提交信息的自动重试或继续。非修复场景允许 required_fix_points 为空；修复场景必须有真实修复目标。
- lineage 保留 anchor_id 和 source_refs，并允许真实 parent_packet_id；根任务不伪造父 Packet。新派生 Packet 使用可区分身份，不能把 checkpoint_id 填为 source_packet_id。
- A2A 输出 handoff_packet、prompt_packet 和 artifact_refs，均关联实际来源 Packet；完整保留 scope、任务身份、风险边界、lineage 及历史。打包本身不执行浏览器、不调用模型、不远程发送；审查备注不能覆盖任务身份或扩大授权。
- 同步计划、探索、验证、证据、评审、修复等必要生产者/消费者及其指令、样例、测试。四个归档入口只在实际转发受到影响时调整。

### checkpoint 定义与执行快照

- checkpoint 定义继续表达可复用步骤、业务断言和适用条件；执行快照另有 snapshot_id、definition_ref、definition_version、captured_at、当前 session_id，以及完整 scope/case/branch/run/lineage。
- 快照须记录当前状态、步骤结果、证据引用及生成 Packet 所需的目标、约束、历史、下一动作。生成器只依赖完整快照，不再临时另传当前任务身份补齐；任务身份在创建快照时从真实当前任务捕获。
- 快照生成主 Packet 时保持 case/branch/run 等任务身份；Packet 身份从快照身份及内容稳定派生，同一快照重复生成可对应同一产物，不同运行快照不能产生同一任务身份。来源链包含快照引用和真实来源 Packet（若有）。
- code_branch 不能冒充测试 branch_id，来源采集时间不能冒充 run.started_at。旧快照、缺少身份、矛盾范围或无法映射的动作必须明确拒绝。
- 快照步骤映射到主 Packet 的动作与风险集合，保留业务断言及证据引用；不能通过丢弃不能识别的步骤制造成功。checkpoint 的 bundle 入口复用统一 A2A 生成逻辑，不维护第二套失真的交接对象。

### 模块就绪与 HTTP 监听

- ModuleReadyContext 使用同一权威布局：scope、case、branch、run、session_id、context_id、checkpoint_id、module_id、目标与登录校验、UI 特征、可选网络证据引用、generated_at、expires_at、handoff_status、evidence_refs。重复出现的身份字段必须一致，module_path 采用统一范围布局。
- ready 要求目标 host、目标路由、登录状态均经实际检查，且与当前会话/运行一致；缺失值不得默认为 true。
- 就绪证据满足两项独立 UI 特征，或一项 UI 特征与本轮匹配的 HTTP 业务证据。重复记录同一特征不计为两项；HTTP 200 或请求出现本身不足以证明业务成功。
- 网络证据记录本轮 run/session、观察时间、请求与响应匹配依据、脱敏业务断言结果和来源引用；只有 UI 自然产生的请求/响应可用。监听不得篡改请求或响应。
- 有效期使用带时区的时间；生成时要求 expires_at 晚于 generated_at，消费时要求 generated_at 不晚于当前时间且当前时间早于 expires_at。时长由当前模块配置明确提供，不静默设置无限有效期。登出、目标改变或会话/运行变化使既有就绪结论失效。
- 全部 ui-test 子 Skill 均取消额外 HTTP 调用、接口重放和主动 API 轮询作为执行、取证、验证、回退或恢复手段。正常授权 UI 自然发出的 GET/POST 可监听；方法名称不构成接口调用例外。无证据时使用两个有效 UI 特征或明确不足，不主动补请求。

### 提交阶段与执行入口

- 复用现有阶段预算和单次令牌机制。默认一个提交；显式声明并获授权的多阶段流程按顺序每阶段一次，阶段 ID 唯一，保持同一 BrowserContext，记录 phase_results 与总 submit_count。
- 阶段前置和提交后业务断言自动执行；重复、乱序、未声明阶段，以及依赖失败/未知结果的后继阶段被拒绝。不能通过新建阶段掩盖重复点击，不对已经授权的完整流程逐阶段或逐请求新增人工审批。
- 删除固定 runner 目录、active resolver、发布 fingerprint/附件摘要匹配作为启动资格。运行用户指定的脚本，不扩展为自动发现和执行任意脚本。
- 新 ExecutionContext/R2ApprovalRecord 删除 active_build_fingerprint、active_attachment_digest 的必需语义，用真实 runner_digest 表达实际脚本来源；原 stable_runner_digest 的固定目录含义不进入新契约。摘要用于真实性与关联校验，不与发布登记匹配以决定运行资格。
- 配置中的 entry_scope 改为指定 runner 的语义；保留真实任务授权、目标和环境、每节点身份、R2 互斥、防重复提交及相关结果链。attempt 的诊断只能表达本次尝试已开始/来源已记录，不再被解释为发布批准。
- 保留 V5 的 execution_context_ref/hash、approval_ref/hash 及必要证据、attempt、事务关联；各生产者、Schema、验证与展示消费者同时更新。不能用空值、占位摘要或假的 active 信息绕过校验。
- 不把本机进程恢复诊断误当机器许可删除；本轮静态检查未发现硬件机器码授权实现。

### V5 报告与历史

- 报告输入保留展示封装与原始 V5 结果的区分：展示元数据、截图和步骤来自实际证据，不能向封闭 V5 对象塞回旧版 scope/release 字段。身份与状态以 V5 为准，关联展示数据有冲突时明确拒绝。
- 复用主 Skill 的 Schema、canonical hash 与证据关联检查。V5 原对象、transaction/session/node 身份、阶段结果及哈希不因报告而重写；报告复制物不是新的提交权威。
- 区分业务节点结果、业务写入状态、产物提交状态和外部验收。提交完成须有真实 manifest/receipt 依据；没有外部验收记录时标明未提供，不从 passed 推导人工验收通过。
- 有效失败 V5 可以报告，缺必需字段、内容篡改、身份冲突、非法状态组合或不支持版本给出具体错误。仅接受 V5，不增加 v2 重新渲染模式；已有历史报告和证据不覆盖。

### 仓库与交付范围

- 先将主 Skill 和九个活跃子 Skill 及必要直接依赖纳入已有本地仓库，保留既有仓库配置；归档入口按受影响程度纳入。复制清单排除凭据、缓存、机器运行产物、私有业务材料和历史工作区。
- 先建立可复现基线并保留现有失败，再按完整行为切片修复。仅做支撑契约共享所必需的前置整理，不借机统一全仓格式或重构无关系统。
- 仓库验证通过后形成准确安装清单；备份安装副本，再同步候选并核对内容。发现用户改动不能盲覆盖；备份与已验证版本须可定位。
- 新增规范字段由对应契约切片固定类型、必需性和拒绝样例并同步所有消费者；不将版本升级当作完成。若发现必须改变已确认业务规则，先回到该决定，不静默扩展范围。

## Testing Decisions

测试边界已经用户确认：实际运行入口＋可见受控网页为主验收，公开产物交接入口证明互通，必要反例复用既有校验和阶段接口。只断言可观察行为与副作用，不锁定私有函数调用顺序。

现有可复用测试依据包括主 Skill 的 pipeline contracts、pytest 插件入口测试、stage write budget、run evidence linker，A2A CLI 测试、checkpoint bundle 测试，以及报告截图和产物校验。它们不等同已存在完整浏览器端到端覆盖；本次补足真正的可见浏览器场景。每个实现切片包含对应生产者、消费者、指令、样例和回归。

| 验收 | 操作与可观察结果 |
| --- | --- |
| AC-001 | 通过报告实际入口输入合法/失败 V5、v2、未知版本、篡改及非法状态组合；合法 V5 可报告并通过产物检查，失败仍失败，旧/非法输入拒绝，历史不变。 |
| AC-002 | 主 Packet 生产入口至 A2A 输出保留完整范围、身份、lineage、历史与证据；缺失/冲突明确报错，不编造父 Packet 或历史。 |

| AC-008 | 在受控页面覆盖取证、验证、回退和恢复路径，结合本地服务器日志及工具调用记录核对只发生 UI 自然请求；无额外 API、重放或主动轮询，敏感值不落盘。 |
| AC-009 | 所有受影响的新入口拒绝旧运行契约自动续跑；从源用例与当前任务生成新产物，已有报告/证据/失败文件保持不变。 |
| AC-010 | 仓库检查通过后完成准确清单、备份与同步；安装内容匹配候选，已有配置和用户改动未无意覆盖，备份可恢复。 |
